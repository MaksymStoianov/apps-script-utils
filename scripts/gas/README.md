# Apps Script runtime tests

The Vitest suite stands in for `SpreadsheetApp`, `SlidesApp`, `Session` and the
rest, so it can only check what the library _asks_ those services to do. These
tests check what the services actually do in response. They create a real
spreadsheet and a real presentation, run the same functions against them, read
the result back, and throw the fixtures away.

They are not part of `npm test`. They need a Google account, they touch Drive,
and they take a minute to run.

## Layout

| File              | Role                                       |
| ----------------- | ------------------------------------------ |
| `bundle.mjs`      | Flattens `dist/` into one Apps Script file |
| `Tests.js`        | The tests and their harness                |
| `appsscript.json` | Project manifest and OAuth scopes          |
| `Library.js`      | Generated by `bundle.mjs`; not tracked     |

## Why a bundler

Apps Script has no module system. It concatenates the files of a project into
a single global scope and rejects `import` and `export` outright, so the
compiled output cannot be pushed as it stands.

`bundle.mjs` strips the module wrappers and emits everything in dependency
order. The ordering is the part that matters: the barrel files make the import
graph cyclic — `exception` imports `lang`, and `lang` imports `exception` — so
a plain topological sort puts some base classes after the classes that extend
them. Function declarations hoist and survive that; `class X extends Y` does
not. The bundler therefore runs a second pass over the inheritance relation
directly, which is what keeps `Exception` ahead of `RuntimeException` ahead of
the concrete classes.

## Running them

```sh
npm run build:gas
cd scripts/gas
clasp create-script --title "apps-script-utils integration tests" --type standalone --rootDir .
clasp push --force
```

Then open the editor and run `runAllTests` once:

```sh
clasp open-script
```

The first run asks for consent to the scopes in the manifest. That consent
cannot be granted from the command line, which is also why `clasp run` will
not work until the project is attached to a standard Cloud project with its
own OAuth client.

Each run writes its report to a document called
`apps-script-utils-test-report` in the root of your Drive, overwriting the
previous one, and logs the same text to the execution log. A document rather
than a text file, because that is what Drive's readers can open.

The manifest also deploys a web app entry point, `doGet`, restricted to the
owner. Once the script has been authorised, a run can be triggered over HTTP
instead of from the editor.

## Reading the result

```text
PASS   appendRows writes below the last populated row
KNOWN  appendColumns writes to the right of the last column
       #450: A1:D1: expected [["a","b","c","d"]], got [["a","b","d",""]]

24 passed, 0 failed, 3 known failures, 0 unexpected passes, 0 skipped
```

`KNOWN` marks a defect the library is already tracking, asserted so that the
run stays green while the bug is open. When one starts reporting
`UNEXPECTED`, the bug is fixed and the expectation should become an ordinary
`PASS`.
